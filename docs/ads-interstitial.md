## 1. 先に訂正：アプリ側の「数秒でスキップ」は作れない

最初の依頼は「数秒間で広告をスキップや削除できるみたいな感じ」でしたが、
**アプリ側（AdMob）では閉じるボタンを自分で作れません。**

| できないこと | 理由 |
|---|---|
| 自前のスキップボタンを付ける | 広告の上に自前のUIを重ねるのはポリシー違反。閉じる操作の近くに広告を置くことも誤クリックの温床として禁じられている |
| 「3秒で閉じられる」と決める | 閉じるボタンが出るまで**最大5秒**。第三者入札の動画では**最大30秒**かかる場合がある |
| 途中で消す | 一度出したら、ユーザーが閉じるまで閉じられない |

**こちらに決められるのは「出すか、出さないか」だけ。** だからアプリ側の要件の中心は
スキップ機能ではなく **頻度** です。うっとうしさは回数で殺します。

**一方、Web側は自社のUIなので自由に作れます。** 「×ボタン」も「3秒で自動的に閉じる」も
できます。最初の依頼にあったイメージは、**Web側でだけ実現できます。**

## 2. 守る順番

`docs/ads.md` の原則は変えません。順番も変えません。

1. 作業を1秒も遅らせない
2. 誤タップを絶対に起こさせない
3. その上で、見てもらえる位置に置く

全画面は 1 と真正面からぶつかります。**だから「作業が完全に終わった瞬間」にしか出しません。**
途中に1回でも割り込ませたら、この要件は失敗です。

## 3. 出すタイミング

### T1 — イベント作成の完了時　【アプリ：広告／Web：誘導】

`/create` で「イベントを作成する」を押し、`/create/done` に着いた直後。

- 操作しているのは**主催者**。既にKOMAROを使うと決めた人なので離脱しにくい。
- ページの切り替わり（Googleが推奨する「コンテンツの切れ目」）に当たる。
- **閉じた後、`/create/done` が普通に見えていること。** この画面には
  「編集者向けURL（必ず保管）」があり、見落とさせると実害が出る。

### T2 — 回答送信の完了時　【アプリ：広告／Web：誘導】

`/e/:id/answer` で送信し、「回答を送信しました！」に切り替わった直後。

- 表示回数はT1より1桁多い。ここが本体。
- ただし操作しているのは**初めてKOMAROに触る参加者**であることが多い。
  最初の体験が全画面広告になるのは、URL共有で広がるサービスとして分が悪い。
- **アプリ側（広告）はT1を2週間動かしてから。** Web側（誘導）は最初から出してよい。
- 実装の注意：完了状態はページ遷移ではなく同じURL（`/e/:id/answer`）のまま
  `submitted` が立つだけ。**URLでは判定できない。** 送信成功のイベントで出す。

### T3 — カレンダーに追加したとき　【Webのみ：誘導】

集計ページの「カレンダーに追加」を押した直後。辻直哉の
「予定追加の時も入れたい、それでサイトに訪れる人多いから」より。

**ここはWebだけ。アプリ版では出しません。** カレンダーアプリへ出ていく操作なので、
戻ってきた瞬間に全画面広告を出すのは体験が悪く、ポリシー上もグレーです。
そもそもこの導線を踏むのはWebの利用者が大半で、
**「アプリを入れてもらう」という目的にいちばん近い場面**でもあります。

リンクの作りが2種類あるので、出し方を分けます。

| 追加先 | リンクの作り | 出し方 |
|---|---|---|
| Google / Yahoo / Outlook / TimeTree / その他 | `target="_blank"`（別タブ） | **元のタブはそのまま残る。** 押した直後にそのタブで誘導を出す |
| Apple | 同じタブで `/cal/apple/...` へ移動 | 元のタブから出ていくので出せない。**移動先の案内ページ**（`app/cal/[type]/[eventId]/route.ts` が返すHTML）に誘導を1つ置く |

### 絶対に出さない場所

- **アプリの起動時・終了時**（ポリシーで禁止。起動時に出すならApp Open広告という別物になるが、やらない）
- **ページを開いた直後**（Web。検索から来た人にいきなり全画面を出すと、Googleの検索順位で不利になる）
- **回答の途中**（`/e/:id/answer` の送信前）
- **イベント作成フォームの途中**（`/create`、ステップ1→2の移動を含む）
- **イベントの修正中**（`/e/:id/edit*`）
- 利用規約・プライバシーポリシー
- コピー・LINE共有など、画面が変わらないボタン操作のあと

## 4. 出す条件

### アプリ版（AdMobの全画面広告）

1つでも外れたら、**何もせず素通りする**。広告のために利用者を待たせない。

| 条件 | 値（提案） | 理由 |
|---|---|---|
| 広告が読み込み済み | 必須 | 未ロードなら待たずに諦める |
| 前回の全画面広告から | 3分以上 | 「1つ閉じた直後に次」はポリシー違反。短い間隔も禁止 |
| 1日の表示回数 | 2回まで | 日程調整は1日に何度もする作業ではない |
| アプリ起動からの経過 | 10秒以上 | 起動直後の表示はポリシー違反 |
| 直前のタップからの間 | 1.2秒以上 | 指の着地点に広告が出ると誤タップになる |

Googleの規定は**ユーザー操作2回につき1回まで**。上の条件はこれよりはるかに厳しい。
加えて**AdMob管理画面側のフリークエンシーキャップ**（1日2回）も設定する。
アプリ側の数え方にバグがあってもGoogle側で止まる。

### Web（アプリ誘導の全画面）

広告ではないのでポリシーの縛りは無いが、**うっとうしければ同じこと**なので上限を決める。

| 条件 | 値（提案） |
|---|---|
| 1日の表示回数 | **1回** |
| ×で閉じられたら | **7日間出さない** |
| 3回閉じられたら | **30日間出さない** |
| 「入手」「追加」を押したら | **二度と出さない** |
| すでにアプリ／ホーム画面から開いている | 出さない |
| 直前のタップからの間 | 0.8秒以上 |

記録は端末のlocalStorage。アカウントが無いサービスなので端末ごとでよい。

## 5. Webの誘導の中身

### 端末ごとの出し分け

既存の `components/AppPromo.tsx` と同じ判断にする。

| 端末 | 出すもの | 押したあと |
|---|---|---|
| iPhone / iPad | 「iPhoneアプリがあります」 | App Store |
| Android / PC（インストール可能なとき） | 「アプリとして追加できます」 | ホーム画面に追加（PWA） |
| すでに入れている | **何も出さない** | — |
| Androidで追加できないとき | **何も出さない** | — |

### 画面の作り

- 画面全体を薄い黒で覆い、中央にカード（アイコン・1行の見出し・1行の説明・大きなボタン）
- **右上に×**。いつでも押せる
- **数秒（提案：5秒）で自動的に閉じる。** 残り秒数は出さない（焦らせない）
- 背景をタップしても閉じる
- 「あとで」の文字リンクも置く
- 閉じたら、元の画面がそのまま見えていること（T1なら編集者向けURL）

> 文言は既存の誘導カードと揃える。**1行に収まる長さを守ること。**
> 2行に折り返すと高さが一気に伸びる（2026-11-06 にカードを84px→66pxへ詰めた経緯あり）。

## 6. 設定（環境変数）

既定はオフ。`docs/ads.md` と同じく、変数を入れた機能だけが動く。

| 変数名 | 役割 | 既定 |
|---|---|---|
| `NEXT_PUBLIC_ADMOB_INTERSTITIAL_ID` | アプリの全画面広告ユニットID | **本番に設定済み** |
| `NEXT_PUBLIC_ADMOB_INTERSTITIAL_ON_CREATE` | アプリ T1 | **本番は `true`** |
| `NEXT_PUBLIC_ADMOB_INTERSTITIAL_ON_ANSWER` | アプリ T2 | `false`（2週間見てから） |
| `NEXT_PUBLIC_APP_PROMO_FULLSCREEN` | Webの誘導全体 | **本番は `true`** |

### AdMobの広告ユニット（2026-11-06 作成）

| 項目 | 値 |
|---|---|
| 広告ユニット名 | `komaro-app-interstitial` |
| ID | `ca-app-pub-3747635667721901/4223667992` |
| フリークエンシー キャップ | **1日2回**（AdMob側。アプリ側の上限と二重にかけてある） |
| 広告の種類 | **テキスト・イメージ・リッチメディアのみ。動画は外した** |

**動画を外した理由。** 動画の全画面広告は閉じるボタンが出るまで最大30秒かかることがある。
日程調整は数十秒で終わる作業なので、30秒待たされるのは致命的。静止画なら閉じるボタンは
ほぼすぐ出る。AdMobは「収益が減る可能性がある」と警告を出すが、ここは体験を取る。
収益が思ったより出ないときに、最初に見直す候補がこれ。

**T1とT2を別の変数にする。** まずT1だけオンにして数字を見るため。
悪化したら変数を消すだけで即座に戻せる。

広告ユニットはAdMob管理画面で新規に作る（バナーとは別のユニット）。

| イベント | いつ |
|---|---|
| `interstitial_shown` / `_dismissed` / `_skipped` | アプリの広告（`placement`・理由つき） |

**見る数字はこの3つ。** 表示回数ではない。

1. **イベント作成数**（T1を入れて落ちたら即やめる）
2. **回答完了数**（T2を入れて落ちたら即やめる）
3. **アプリのダウンロード数**（Webの誘導が効いているか）

| リスク | 程度 | 対策 |
|---|---|---|
| 初めての参加者が離脱する | **高**（アプリT2） | T1を先に入れて2週間見る |

## 13. Web側の全画面広告（ビネット）— 審査が降りたら

辻直哉「使い勝手よくしたものがアプリなら、webでも全画面広告出るようにしたらいいんじゃない？」より。

### できること・できないこと

| | |
|---|---|
| 出し方 | 自動広告の**オーバーレイ フォーマット → ビネット広告**だけをオンにする |
| 本文への差し込み | **起きない。** ページ内フォーマットはオフのままにする |
| 出る場所 | **選べない。** Googleがページの移動のたびに判断する |
| 頻度 | **選べる。** 1分〜1時間。既定は10分 |
| ページ除外 | できるが**前方一致のみ。** `/e/<id>/answer` のようにIDが挟まるパスは指定できない |

### 決めること

- **頻度は1時間にする。** 既定の10分では、1回の日程調整の中で複数回出る。

  頻度は「**前のビネットを出してから次まで空ける時間**」であって、初回を遅らせる設定ではない。
  初めて来た人は最初から対象で、1時間にしても**1本目は普通に出る**。1時間が効くのは
  同じ人への2本目以降だけなので、**広告の数はほとんど減らない**。減るのは
  「同じ人に連続で出る」分で、それはそもそも出したくない分。

  参加者の動きは「集計を見る → 回答する → 送信 → 集計を見る」でページの移動が2回あるため、
  出る機会はある（送信の完了は画面が切り替わらないので、そこでは出ない）。

  > Googleのヘルプに「初回は即座に出る」と明記はない。「最後に出してから」という
  > 書き方からの読み。オンにしたら実際の数字で確かめること。
- **ページ除外は使えない。** 回答画面だけを外したくてもIDが挟まるので指定できない。
  ただしビネットは**ページの移動のときに出る全画面**であって、本文には入らない。
  送信ボタンの隣に広告が出るわけではないので、誤タップの危険はバナーより小さい
- **自前の全画面誘導と同時に出さない。** ビネットをオンにしたら
  `NEXT_PUBLIC_APP_PROMO_FULLSCREEN` を切る。全画面が2回続くのが最悪

### 分かっていて引き受けるリスク

KOMAROの利用者の大半は、**LINEで送られてきたURLを1回開いて、回答して、二度と来ない参加者**です。
その人たちにとって全画面広告はただの邪魔で、アプリを入れる動機にはなりません
（1回の日程調整のためにアプリは入れない）。そしてこのサービスを広げているのは、
その参加者が次は主催者になる流れです。

「アプリの方が快適だからWebは多少不便でよい」という考え方は、**何度も使う主催者には効きますが、
一度きりの参加者には効かず、その人たちが広がりを作っている**という点だけ、頭に置いておくこと。
頻度を1時間にするのはそのための防波堤です。

**オンにしたら回答完了数を2週間見ること。** 落ちたら頻度を下げるか、切る。

## 14. アプリ側の実装（2026-11-06 完了）

| ファイル | 役割 |
|---|---|
| `lib/taskDone.ts` | 「作業が終わった瞬間」の通知。Webの誘導と共通 |
| `components/NativeInterstitial.tsx` | 全画面広告の本体。レイアウトに1つだけ置く |
| `lib/admob.ts` | SDKの初期化（バナーと共通） |
| `lib/ads.ts` | 設定と、場面ごとの出す・出さないの判定 |

iOSシミュレーターで、Googleのテスト広告ユニットを使って確認したこと：
作成完了で全画面広告が出る／×で閉じると完了画面（編集者向けURLが見える状態）に戻る／
3分以内の2回目は出ない／作成フォームの途中では出ない。

### 直した不具合

**バナーを出さずに全画面広告だけを有効にすると、広告が出なかった。**
AdMob SDKの初期化をバナーのコンポーネントが抱えていたため、バナーが無効だと
SDKが初期化されないまま読み込みに失敗していた。初期化を `lib/admob.ts` に出して、
どちらからでも1回だけ走るようにした。**片方だけオンにできる作りなのに、
片方がもう片方に依存していた**のが原因。
