# KOMARO 広告設計

日本語メモ:

- このファイルは、KOMAROに広告を入れるときの設計と運用ルールをまとめたものです。
- 実装は済んでいますが、**環境変数が未設定のため現在は広告が一切表示されません**（コードも読み込まれません）。
- 有効化に必要な作業は `docs/todo-for-owner.md` の「広告」節にまとめてあります。

---

## 1. 何を最優先にしたか

KOMAROは「日程調整を最短で終わらせる」ための道具です。道具の価値は、使っていて摩擦がないことに宿ります。したがって広告設計の原則を次の順で置きました。

1. **作業を1秒も遅らせない**
2. **誤タップを絶対に起こさせない**
3. **その上で、見てもらえる位置に置く**

この順序を守ると「広告があること自体は気づくが、邪魔だとは感じない」状態に落ち着きます。逆に順序を入れ替えると、短期の収益と引き換えに再訪率を失います。日程調整ツールは口コミとURL共有で広がるため、体験の毀損は集客の毀損に直結します。

## 2. 掲載してよい場所・ダメな場所

### 置く場所（実装済み）

| 枠 | 位置 | 選定理由 |
|---|---|---|
| `summaryBottom` | 集計ページ（`/e/[id]`）の最下部、コメント欄より下 | **最重要枠**。参加者全員が必ず開くページで閲覧数が最も多く、集計表という実質的な中身があるためAdSenseの品質要件も満たしやすい |
| `homeBottom` | トップページのCTAより下 | 検索流入の受け皿。読み物としての体裁がある |
| `helpBottom` | ヘルプページ最下部 | 滞在時間が長い。FAQを読み終えた後で注意が空く |
| `answerComplete` | 回答送信の完了画面 | 作業が完全に終わった直後。ここで数秒奪っても失うものがない |
| `createComplete` | イベント作成の完了画面、操作ボタンより下 | 同上。ただしURLのコピー導線と離すため余白を広めに取っている |
| `summaryUnderTable` | 集計表の直下（PCは左カラム内、スマホは表と参加者一覧の間） | **表を見た直後で視線がそこにある**ため、最下部枠より確実に見られる。引き換えに参加者一覧が下へ押し下がる |
| `summarySidebar` | 集計ページのサイドバー下部（**PC専用**） | もともと空いている余白。**何も押し下げないのでレイアウトが変わらない**。縦長300pxが入るので単価も高い。スマホでは出ないため量は限定的 |
| `answerBottom` | 回答画面・送信ボタンの**128px下** | 表示回数は最多クラス。ただし下記の注意を必ず読むこと |
| `homeMiddle` | トップページ、機能紹介とCTAの間 | 読み物の切れ目で割り込み感が小さい。ただしトップは通過点で滞在が短く、表示回数は最少 |

#### ⚠️ `answerBottom`（回答画面）の注意

**送信ボタンの真下は、スマホで親指が着地する位置です。** 誤タップは広告主への無効クリックとして
計上され、**AdSenseアカウント停止の直接の原因**になります。

そのため `app/e/[eventId]/answer/page.tsx` では、送信ボタンとの間に `h-32`（128px）の
余白を明示的に挟んでいます。**この余白を詰めないでください。** 詰めるくらいなら枠を外す方が安全です。

2026-10-18 に辻直哉の判断で枠を用意しましたが、5枠のうち**最後に有効化する**ことを勧めます。

#### `summarySidebar` がPC専用である理由

スマホでは2カラムにならず、ただの差し込みになるため、`minWidth={768}` を指定しています。
**CSSで隠すのではなく要素ごと描画しない**実装です。`display:none` の中で広告を要求すると、
見えていない広告のリクエストが発生し、AdSenseのポリシー上の問題になるためです。

### 絶対に置かない場所

- **回答中のコマ表の周囲**（`/e/[id]/answer`）— 誤タップが起きると、広告主に無効なクリックが計上されてAdSenseアカウントの停止理由になり、利用者にとっては「押してないのに広告が開いた」体験になります。二重に損です。
- **画面に追従するバナー・全画面広告（インタースティシャル）** — 日程調整は数十秒で終わる作業です。そこに割り込む広告は、得られる単価に対して離脱の代償が大きすぎます。
- **1画面に2枠以上** — 密度を上げると単価は下がり、体験だけが悪くなります。
- **利用規約・プライバシーポリシー** — 信頼を担保するページに広告は置きません。

## 3. 実装上の作り込み

- **既定はオフ**。`NEXT_PUBLIC_ADS_ENABLED` が `true` でなければ、広告スクリプトのタグ自体をページに出しません。設定ミスで意図せず広告が出ることがない作りです。
- **完了画面は「帯」で区切る**（`variant="section"`）。回答送信後・イベント作成後の画面は下に余白が余るため、そこへ収める代わりに、区切り線と薄い背景で画面端まで伸びる帯にして「ここから先はアプリの中身ではない」と一目で分かるようにしています。最後の操作ボタンとの間には約90pxの余白を空け、誤タップを防いでいます。
- **枠ごとに個別のオン・オフ**。環境変数を枠ごとに分けてあるため、まず集計ページだけで試して、数字を見てから増やせます。
- **配信されなかったときは枠ごと消える**。AdSenseが広告を返さなかった場合（`data-ad-status="unfilled"`）、空白を残さず要素ごと削除します。広告ブロッカーで読み込めない場合も4秒でたたみます。
- **レイアウトのガタつきを防ぐ**。表示が確定するまで120pxの高さを確保し、後から下の要素が押し下げられないようにしています。
- **非パーソナライズ広告のみ**（既定）。閲覧履歴に基づく出し分けをしません。
- **ネイティブアプリ内では表示しない**（次節）。
- **ads.txt** を `/ads.txt` で自動配信します。これが無いとAdSense側で警告が出て収益が制限されます。
- **プライバシーポリシーが自動で追従**。広告をオンにすると、プライバシーポリシーの第5節・第7節に広告配信とCookieの記載が自動で現れます。オフに戻せば消えます。記載漏れによる規約違反が起きない作りです。

## 4. 重要な制約：アプリ内にAdSenseは入れられない

KOMAROのiOS/Android版は `komaro.app` をWebViewで表示する構造ですが、**AdSenseの広告をアプリ内に表示することはAdSenseのポリシー違反**です（AdSenseはウェブサイト向け、アプリ向けはAdMob）。違反した場合、Webサイト側を含むAdSenseアカウント全体が停止される可能性があります。

そのため `AdSlot` は `Capacitor.isNativePlatform()` を見て、**アプリ内では広告を描画せず、スクリプトも読み込みません**。

アプリでも広告を出したい場合は、別途AdMobの導入が必要です（`@capacitor-community/admob` などのプラグイン追加、AdMobアプリID・広告ユニットIDの取得、iOSはATT（アプリのトラッキング透明性）対応とApp Storeの「App Privacy」申告の更新）。**初回のApp Store申請は広告なしで出すことを強く勧めます**。理由は次の2つです。

1. 現状でもガイドライン4.2（Webサイトの再パッケージ）でのリジェクトリスクを抱えており、広告が入ると「広告を出すためだけのラッパーアプリ」と見なされる余地が増えます。
2. 広告SDKを入れると「App Privacy」の申告項目とATTの実装が必要になり、審査で確認される項目が増えます。

## 5. 収益の現実的な見積もり

正直に書きます。**今の規模では広告収益はほぼ出ません。**

- 現在のイベント作成数は約190件。1イベントあたり参加者5〜10人が集計ページを1〜2回開くとして、**月間のページビューはおよそ1,000〜3,000**。
- 日本語サイトのAdSenseのRPM（1,000ページビューあたりの収益）は、この種のツール系サイトで概ね**200〜500円**。
- したがって**月間200〜1,500円程度**が期待値です。非パーソナライズ広告のみにしているため、実際はこの下限寄りになります。

つまり、広告は**いま入れても生活を変える金額にはならない**一方で、体験を落とすと成長を止める危険はあります。私の推奨は次のとおりです。

- **仕組みは作っておく（済み）。いつでも1分でオンにできる状態を確保する。**
- **オンにするのは、月間ページビューが1万を超えてから**。そこで初めて月数千円規模になり、サーバー費用（Vercel・Neon）を相殺し始めます。
- それまでは、同じ時間を**参加者→主催者の転換率**（既に実装済みのCTA）と**検索流入**に使うほうが、最終的な広告収益も含めて大きくなります。ページビューが10倍になれば広告収益も10倍になりますが、広告を最適化しても2倍にはなりません。

## 6. 有効化の手順

### 現在の状態（2026-10-15）

| 項目 | 状態 |
|---|---|
| AdSenseアカウント | 作成済み（`naoyattsuji@gmail.com`／**t が2つ**） |
| パブリッシャーID | `ca-pub-3747635667721901`（設定・デプロイ済み） |
| サイトの所有権確認 | ✅ **ads.txt 方式**で完了 |
| サイト審査 | リクエスト済み・結果待ち |
| 自動広告 | オフ（確認済み） |
| 広告ユニット | `komaro-summary-bottom` = `4670802271`（設定・デプロイ済み） |
| 実際の配信 | 審査承認まで `unfilled`（枠ごと非表示）。承認後に自動で出る |
| お支払い情報 | **未入力（本人のみ）** — これが無いと承認されても配信されない |


AdSenseは「アカウント審査 → 承認 → 広告ユニット作成」の順で、審査中は広告ユニットIDが存在しません。そのため2段階に分かれます。

### 第1段階: 審査を通す（パブリッシャーIDだけを設定する）

AdSenseのアカウントを作ると `ca-pub-XXXXXXXXXXXXXXXX` というパブリッシャーIDが発行され、「サイトにこのコードを設置してください」と指示されます。KOMAROでは、**パブリッシャーIDを設定するだけで審査用のコードが `komaro.app` 全体に入ります**（広告枠はまだ出ません）。

```bash
vercel env add NEXT_PUBLIC_ADSENSE_CLIENT production   # ca-pub-XXXXXXXXXXXXXXXX
vercel --prod
```

デプロイ後、AdSense管理画面で「コードを設置しました」を押して審査を依頼します。審査は数日〜2週間程度。

### 第2段階: 承認後に広告を出す

承認されたら広告ユニット（ディスプレイ広告）を作り、ユニットID（数字列）を控えて設定します。

```bash
vercel env add NEXT_PUBLIC_ADS_ENABLED production                  # true
vercel env add NEXT_PUBLIC_ADSENSE_SLOT_SUMMARY_BOTTOM production  # 数字のユニットID
vercel --prod
```

最初は `SUMMARY_BOTTOM` の1枠だけで1〜2週間運用し、離脱率とイベント作成数が落ちていないことを確認してから他の枠を足してください。数字が悪化したら、環境変数を消すだけで即座に元に戻せます。

#### 枠の位置を実機で見る（`?ads=preview`）

URLに `?ads=preview` を付けると、**全9枠の位置にダミーの枠が出る**。広告ユニットIDが
未設定の枠も含めて出るので、有効化を決める前にPCとスマホで位置と見え方を確認できる。

```
https://komaro.app/?ads=preview
https://komaro.app/e/<イベントID>?ads=preview
https://komaro.app/e/<イベントID>/answer?ads=preview
https://komaro.app/help?ads=preview
```

- **AdSenseのコードは一切読み込まず `adsbygoogle.push` もしない**ため、無効な
  インプレッションは発生しない。本番に付けたまま誰かが開いても害はない。
- ネイティブアプリ内と、画面幅の条件を満たさない枠（`summarySidebar` をスマホで見た場合など）は
  従来どおり描画しない。**スマホでサイドバー枠が出ないのは正しい挙動**。
- 画面遷移するとクエリは外れるので、確認したいページごとにURLへ付け直すこと。

#### 枠を増やす推奨順

全9枠の実装は済んでいます。**環境変数に広告ユニットIDを入れた枠だけが出る**ので、1枠ずつ試せます。

1. `SUMMARY_BOTTOM`（設定済み）
2. `SUMMARY_SIDEBAR` — PC専用で何も押し下げないため、体験への影響が最も小さい
3. `SUMMARY_UNDER_TABLE` — 最も稼げる枠。参加者一覧が下がるので、入れた後に**イベント作成数と離脱率を必ず見る**
4. `HOME_MIDDLE` / `HELP_BOTTOM` / `HOME_BOTTOM` — 流入の受け皿。影響は小さい
5. `ANSWER_COMPLETE` / `CREATE_COMPLETE` — 作業完了後なので安全
6. `ANSWER_BOTTOM` — **最後**。上の注意を読んでから

### ⚠️ 自動広告（Auto ads）は必ずオフにすること

AdSense管理画面には、Googleが勝手に広告の位置を決める「**自動広告**」という機能があります。**これをオンにすると、このドキュメントで設計した掲載位置が全て無視され、回答中のコマ表の上や画面追従バナーにも広告が入ります。** 誤タップによる無効クリックが発生し、アカウント停止のリスクにも直結します。

サイト追加時に既定でオンになっていることがあるため、**AdSense管理画面 → 広告 → サイトごとの設定で「自動広告」がオフになっていることを必ず確認してください。**

### 所有権の確認は ads.txt 方式で行うこと（AdSenseコード方式は失敗する）

AdSense の「サイトの所有権を確認してください」には3つの方式があるが、**`AdSense コード スニペット` 方式は必ず失敗する**（2026-10-15 に確認）。

理由は、審査用スクリプトをサーバー側HTMLではなくブラウザ側で挿入しているため（`components/AdSenseScript.tsx`）。これは**ネイティブアプリのWebView内で読み込まないようにするための設計**であり、不具合ではない。AdSense のクローラは生のHTMLを読むため、スクリプトタグが見つからない。

**`ads.txt スニペット` 方式を選ぶこと。** `app/ads.txt/route.ts` がパブリッシャーIDから自動生成して配信しているので、`NEXT_PUBLIC_ADSENSE_CLIENT` が設定されていれば追加作業なしで通る。

サーバー側で出力する方式へ切り替えることもできるが、その場合はアプリのUser-Agentで除外する対応が別途必要になり、取りこぼすとポリシー違反（アカウント停止）に直結するため、ads.txt 方式を推奨する。
